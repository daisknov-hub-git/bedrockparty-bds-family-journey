BDSに家族3人で入りたいだけだった
――20日以上と3連休を注ぎ込んだ、しがないDTPオペレーターとChatGPTのBedrockParty奮闘記

はじめに

私はプログラマーではありません。ネットワークエンジニアでもありません。普段はIllustratorや業務ソフトを使って仕事をしている、しがないDTPオペレーターです。

そんな私がやりたかったことは、とても単純でした。

家族3人でMinecraftを遊びたい。

Windows PCにBedrock Dedicated Server（以下BDS）を立てて、Nintendo
SwitchやPS5から、家族それぞれのMicrosoftアカウントで同じワールドに入りたい。それだけです。

少なくとも、始めたときは「それだけ」のつもりでした。

ところが気がつけば、Docker
Desktopを入れ、WSLでUbuntuを動かし、BedrockPartyとNetherNet
Bridgeを調べ、ICE candidateを追いかけ、Microsoft OAuth
TokenとXUIDを調査し、最後にはGoのソースコードまで変更していました。

途中には3連休もありました。まとまった時間が取れます。

結果、3日ともこれをやっていました。

検証期間は20日以上。その間、ほぼずっと隣にいたのがChatGPTでした。

私がログを貼る。ChatGPTが原因を考える。「次はこれを確認しましょう」と言われる。実行する。失敗する。ログを貼る。また次を試す。

一つ変える。再起動する。確認する。ダメなら戻す。

そうやって、一枚ずつ問題を剥がしていきました。

この記事は「この設定をコピーすれば必ず動きます」という万能マニュアルではありません。MinecraftもBDSもBedrockPartyも更新されますし、環境が違えば結果も違うでしょう。

これは、私の環境で何が起き、どう切り分け、最終的に家族3人が同時にBDSへ入れるようになったのか。その過程を、成功だけでなく失敗も含めて残す記録です。

同じところで立ち往生した誰かに、一つでも手掛かりが残れば十分です。

第6章　Identityを追いかける

Identityは正しい。それなら、そのIdentityをBDS側まで保持すればいいのではないか。

そこでgophertunnel側も含め、Identityがどう扱われているのかを確認しました。incoming側のIdentityを保持するための修正を試します。

しかし、それだけでは解決しません。

Incoming IdentityはChild-Aなのに、backend側のMultiplayer
Tokenは依然として親です。

ここで、

Minecraft
Identityを保持することと、BDSへ接続するときのMicrosoft認証Identityは別の問題らしい

と分かってきました。

私はこの仕組みを最初から理解していたわけではありません。ログをChatGPTへ渡し、コードのどこを通っているのか確認し、デバッグ出力を追加して、もう一度接続する。

その繰り返しです。

そしてBridgeのソースコードを追っていくと、Microsoft認証の重要な部分に辿り着きました。

元の処理は概念的には、

token, err := auth.RequestLiveToken() tokenSource :=
auth.RefreshTokenSource(token)

という形でした。

Bridge起動時にMicrosoft認証を行い、そのTokenSourceをbackend側の接続でも使用します。

一人なら問題ありません。

しかし、今回は家族3人が別々のMicrosoftアカウントで入ります。

Parent ───────────────┐ │ Child-A ───────────────┼──→ NetherNet Bridge │
Child-B ───────────────┘ │ │ Shared TokenSource ▼ │ ▼ BDS

これなら、入口で誰が来ても出口ではBridgeが認証しているアカウントになります。

あの現象の意味が、ようやく見えました。

子どもが途中で父親に変身していたわけではありません。Bridgeが出口で父親のMicrosoft
Tokenを使っていたのです。

念のためBridgeを子どものMicrosoftアカウントで認証してみると、

MULTIPLAYER_TOKEN_DEBUG xid= xname=

になりました。

Bridgeを親で認証すれば親。子どもで認証すれば子ども。

必要なのは、Bridgeへ入ってきたプレイヤーに応じて、backendで使うMicrosoft
Tokenも切り替えることでした。

第7章　DTPオペレーター、Goのソースコードを触る

私はDTPオペレーターです。普段の仕事で使うのはIllustratorや業務用の組版システムです。

その私が休日に、「incoming
XUIDに応じてTokenSourceを切り替えるにはどうすればいいか」を調べています。

どうしてこうなった。

もちろん、自分でゼロからプログラムを書いたわけではありません。ChatGPTと一緒に「このログなら次はここを見る」「ここへデバッグを追加する」「この処理を変更する」と、一つずつ進めました。

考えた仕組み自体はシンプルです。

プレイヤーごとにXUIDが違う。それなら、XUIDをキーにして、そのプレイヤー専用のMicrosoft
OAuth Tokenを選ぶ。

Parent ── XUID A ── Token A ──┐ │ Child-A ── XUID B ── Token B ───┼──→
Bridge → BDS │ Child-B ── XUID C ── Token C ───┘

XUIDからTokenファイルを選択する処理を追加しました。公開用に値を置き換えると、概念的にはこうなります。

func tokenPathForXUID(xuid string) (string, bool) { switch xuid { case
“”: return “/data/nethernet/.json”, true case “”: return
“/data/nethernet/.json”, true case “”: return “/data/nethernet/.json”,
true default: return ““, false } }

つまり、

Incoming XUID ↓ tokenPathForXUID() ↓ そのXUID専用のOAuth Token ↓
Multiplayer Token ↓ BDS

という流れです。

コードのすべてを理解していたかと言われれば、そうではありません。

ただ、何を変えたのか。そして変えた結果、ログがどうなったのか。

そこだけは一つずつ確認しました。

第9章　今日動いただけでは困る

3人同時接続には成功しました。しかし、家族で普段使うサーバーです。起動するたびにMicrosoft認証をやり直すようでは困ります。

そこでTokenSourceをラップし、更新されたTokenをプレイヤーごとのファイルへ保存する処理を追加しました。

type persistingTokenSource struct { src oauth2.TokenSource path string
mu sync.Mutex }

func (p persistingTokenSource) Token() (oauth2.Token, error) {
p.mu.Lock() defer p.mu.Unlock()

    token, err := p.src.Token()
    if err != nil {
        return nil, err
    }

    if err := saveLiveToken(p.path, token); err != nil {
        return nil, err
    }

    return token, nil

}

Bridge側では、

tokenSource := &persistingTokenSource{ src:
auth.RefreshTokenSource(token), path: tokenPath, }

とします。

Tokenファイルを保存するディレクトリはDockerへ、

volumes: - “./secrets/nethernet:/data/nethernet:rw”

としてマウントし、さらに、

secrets/

を .gitignore に追加しました。

これは公開時にも非常に重要です。実際のOAuth Tokenやrefresh token、device
code、private keyなどは絶対に公開しません。

この記事でも、Microsoft/Xboxアカウント名、XUID、家庭内LAN
IP、Windowsユーザー名など、個人や家庭環境につながる情報は削除または匿名化しています。

第12章　うまくいかなかったことにも意味があった

成功した設定だけを書けば、この記事はもっと短くできます。

でも今回の場合、失敗したことにもかなり価値がありました。

candidatesが0になりました。Incoming
Identityだけを保持しても複数アカウント問題は解決せず、backend側のMicrosoft
Multiplayer Tokenまで一致させる必要がありました。

1つのMicrosoft
TokenSourceを全員で共有すると、backend側では同じIdentityになります。同じMicrosoftアカウントをSwitchとPS5で使う方法も、今回の家族同時プレイには向きませんでした。

UDP 19132だけでBDSの起動を判定すればDocker
backendを誤認し、BDSを雑に強制終了するのも避けたかった。

一つ直ると、その向こうから次の問題が出てくる。

ほぼずっとこれでした。

最終的には、

Parent ── XUID A ── OAuth Token A ──┐ │ Child-A ── XUID B ── OAuth Token
B ───┼──→ Bridge → BDS │ Child-B ── XUID C ── OAuth Token C ───┘

という構成になりました。

今回の複数アカウント問題を一行で表すなら、

Incoming Identity ≠ Backend Microsoft Identity

だったものを、

Incoming Identity = Backend Microsoft Identity

にした。

これが核心だったと思います。
